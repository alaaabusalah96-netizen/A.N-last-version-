# استراتيجية قواعد البيانات (Database Strategy)

## 1. استقلالية محرك قاعدة البيانات (Engine-Agnostic via Adapters)
تم تصميم طبقة استمرارية البيانات بحيث تكون مستقلة تمامًا عن أي محرك قاعدة بيانات بعينه، وذلك عبر:
- **واجهات المزود (Database Provider Interfaces)**: واجهات TypeScript مجردة تحدد العمليات الأساسية (الاستعلامات، المعاملات، الإدارة، الفهارس).
- **محولات المحركات (Database Adapters)**: تطبيق عملي للواجهة لكل محرك مستهدف.
- **المحرك المرجعي لـ V1**: هو محرك **PostgreSQL**.
- أي محرك قاعدة بيانات إضافي لن يتم إعلان دعمه إلا بعد بناء محوله واجتيازه لاختبارات توافق معيارية صارمة ومستقلة.

## 2. إدارة الاتصالات وتوجيه المستأجرين (Registry & Resolver)
تتضمن البنية التحتية مكونين رئيسيين لإدارة قواعد البيانات وتعدد المستأجرين:

### أ. سجل الاتصالات (Connection Registry)
- يدير تجمعات الاتصال (Connection Pools) النشطة لكل قاعدة بيانات مسجلة.
- يتحكم في صحة الاتصال (Health Checks)، مهلات الاتصال (Timeouts)، وإعادة الاتصال الآمنة.

### ب. محدد قاعدة بيانات المستأجر (Tenant-to-Database Resolver)
- مكون مسؤول عن فك شفرة سياق المستأجر (Tenant Context) من الطلب الوارد وتوجيهه فورًا إلى تجمع الاتصال المخصص له.
- يضمن عدم اختلاط البيانات بين المستأجرين وتطبيق سياق العزل تلقائيًا.

## 3. أنماط الاتصال والتخزين المعتمدة (وموقف النمط الهجين)
*(محدّث 2026-11-12 — تاريخيًا طرحت الوثيقة 4 أنماط، ثم اعتُمدت 3 أنماط فقط مع رفض النمط الهجين معماريًا)*

تدعم المنصة فعليًا في التنفيذ المرجعي (`TenantDatabaseResolver`) **ثلاثة أنماط معتمدة فقط** (`central` / `per_company` / `on_prem`):

1. **النمط المركزي المشترك (`central` — Multi-Tenant Shared Database)**:
   - كافة الشركات تتشارك نفس قاعدة البيانات ونفس المخطط مع عزل منطقي صارم بناءً على `company_id` وسياسات RLS المفروضة.
2. **نمط قاعدة مستقلة لكل شركة (`per_company` — Dedicated Database per Tenant)**:
   - لكل شركة قاعدة بيانات خاصة بها معزولة فيزيائيًا على نفس الخادم أو خوادم سحابية منفصلة عبر توجيه صريح في `TenantDatabaseResolver`.
3. **نمط قاعدة محلية بمقر الشركة (`on_prem` — On-Premises Tenant Database)**:
   - ربط المنصة بقاعدة بيانات موجودة محليًا في مركز بيانات الشركة أو خوادمها الداخلية (عبر شبكة آمنة أو VPN) مع توجيه صريح في السجل.
4. **النمط الهجين (Hybrid Mode) — مرفوض معماريًا (محدّث 2026-11-12)**:
   - كان مطروحًا مبدئيًا لتقسيم العمليات الحساسة محليًا والسجلات سحابيًا، لكنه **مرفوض معماريًا** في التنفيذ الفعلي لأن توزيع قيود المحاسبة والمخزون والمعاملات عبر قاعدتين منفصلتين يكسر الذرية الموزعة وسلامة المفاتيح المركبة؛ وبناءً عليه يرفض `src/server/db/TenantDatabaseResolver.ts` قيمة `hybrid` صراحة (`DB_MODE_INVALID: mode 'hybrid' is not supported — choose central, per_company or on_prem`).

### ضوابط التنفيذ الإلزامية في طبقة القواعد
- **عدم التحويل الصامت لقاعدة افتراضية (Fail-Closed Routing)**: عند ضبط `DB_MODE` على `per_company` أو `on_prem` وعدم وجود مسار صريح مسجل للشركة، يرفض `TenantDatabaseResolver.resolve` الطلب بخطأ `TENANT_DB_ROUTE_MISSING` ولا يُحوّل أبدًا إلى القاعدة المركزية الافتراضية بصورة صامتة.
- **منع DDL التلقائي أثناء التشغيل (No Runtime DDL)**: يعمل تطبيق الخادم بدور تطبيقي مقيد الصلاحيات (`an_app`) محروم من إنشاء الجداول أو تعديل المخطط وقت التشغيل؛ وتُنفذ التغييرات البنيوية حصرًا عبر ترحيلات مضبوطة (`npm run migrate` عبر `MIGRATION_DATABASE_URL`).
- **دور المهيئ (Provisioner Role)**: إنشاء وتخصيص أدوار/امتيازات التشغيل يُدار حصرًا عبر مسار التهيئة المنضبط (`scripts/provisionAppRole.ts` / دور Provisioner المخصص) وليس داخل مسارات الطلبات الاعتيادية.

## 4. حوكمة اختيار محرك قاعدة البيانات
- **من يختار محرك قاعدة البيانات؟**:
  - **مسؤول المنصة / مسؤول النشر والتشغيل فقط (Platform / Deployment Administrator)** عبر إعدادات النشر ومصفوفات التكوين المعتمدة.
  - يُمنع منعًا باتًا تمكين المستخدم العادي أو مدير الشركة داخل واجهة التطبيق من تغيير محرك قاعدة البيانات أو التلاعب بمستويات الاتصال.

## 5. الترحيل المنضبط بين القواعد والمحركات (Controlled Migration)
- نقل شركة أو مستأجر من قاعدة بيانات إلى أخرى أو من محرك إلى آخر لا يتم عبر زر إعداد بسيط في الواجهة.
- يتم الترحيل كعملية هندسية منضبطة تشتمل على المراحل التالية:
  1. التحقق المسبق من التوافق وجاهزية الوجهة (Pre-flight Validation).
  2. قفل بيانات المستأجر مؤقتًا لمنع التعديلات أثناء النقل (Read-Only Locking).
  3. استخراج البيانات والتحويل المتوافق وتدقيق التماسك (Export & Checksum Audit).
  4. استيراد البيانات في الوجهة الجديدة والتأكد من مطابقة السجلات والقيود.
  5. تحديث سجل التوجيه (Resolver Update).
  6. وجود خطة رجوع تلقائية وموثقة (Rollback Plan) في حال فشل أي خطوة.

## 6. الفصل الحاسم بين المفاهيم: دعم المحرك مقابل التشغيل دون إنترنت
- **دعم محرك قاعدة بيانات محلي أو خارجي**: يعني قدرة المنصة عبر بروتوكولات الشبكة على التحدث إلى قاعدة بيانات تعمل محليًا أو سحابيًا بنجاح.
- **التشغيل الكامل للنظام دون إنترنت (Full Offline)**: يعني تشغيل خادم التطبيق وواجهته وقاعدته بالكامل دون وجود أي شبكة خارجية مع مزامنة لاحقة.
- **التأكيد**: دعم محركات مختلفة أو قواعد محلية لا يعني إطلاقًا أن النظام يعمل بكامله Offline؛ مسار الـ Offline مسار مستقل بالكامل وغير موعود في الإصدار V1.
