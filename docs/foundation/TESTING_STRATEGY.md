# استراتيجية الاختبارات والتحقق (Testing Strategy)

## 1. الفلسفة الأساسية للاختبار
- **عدم كفاية النجاح الشكلي**: مجرد نجاح تجميع الكود (`npm run build` أو `tsc --noEmit`) لا يُعد إطلاقًا دليلاً كافيًا على صحة النظام أو سلامة منطق الأعمال.
- تُبنى جودة النظام المالي والمخزني على أدلة ملموسة وتحقق عملي مستمر تغطي كافة المستويات الهندسية.

## 2. هرم الاختبارات ومستوياتها

### أ. اختبارات الوحدة (Unit Tests)
- تغطي منطق الأعمال الصافي في طبقة النطاق (Domain Entities, Value Objects, Domain Services).
- التحقق الرياضي الصارم من موازين القيود، حسابات الضرائب، تقييم المخزون، والعملات.
- سريعة وتعمل بالكامل في الذاكرة دون اتصال خارجي.

### ب. اختبارات التكامل (Integration Tests)
- اختبار تواصل محولات قواعد البيانات (Database Adapters) مع المحرك المرجعي PostgreSQL.
- اختبار المعاملات الذرية وحالات التراجع (Rollback on Error) لضمان عدم حفظ قيود غير متوازنة.
- اختبار محدد المستأجر (Tenant Resolver) والتأكد من عدم تسرب البيانات بين جلستين متزامنتين.

### ج. اختبارات واجهات البرمجة (API / Contract Tests)
- التحقق من التزام الخادم بنصوص ومواصفات OpenAPI / REST.
- التحقق من صحة كود الاستجابة (HTTP Status Codes)، بنية رسائل الخطأ، وصحة تصفية البيانات المدخلة والمخرجة.

### د. اختبارات الأمان والحماية (Security Tests)
- التحقق من رفض أي طلب يفتقر إلى مصادقة صحيحة.
- محاولات اختراق مصطنعة للوصول إلى بيانات شركة أخرى عبر التلاعب بمعرف المستأجر (IDOR).
- فحص قيود معدل الطلبات (Rate Limiting) وضوابط جلسات المستخدمين.

### هـ. اختبارات النهاية إلى النهاية (End-to-End Tests)
- محاكاة سيناريوهات كاملة تبدأ من واجهة المستخدم:
  - إنشاء أمر بيع -> إصدار فاتورة -> خصم المخزن -> توليد القيود -> فحص ميزان المراجعة.

## 3. مجلد الأدلة وإثبات الجودة (Evidence Standard)
- يتم إنشاء مجلد مخصص للأدلة باسم `evidence/` لكل حزمة عمل (مثل `evidence/p00`, `evidence/p01`).
- تُحفظ فيه مخرجات الاختبارات، تقارير التغطية، لقطات السجلات أو نتائج الفحص الأمني لتكون مرجعًا قابلاً للمراجعة والتدقيق الإنساني قبل اعتماد أي مرحلة.
